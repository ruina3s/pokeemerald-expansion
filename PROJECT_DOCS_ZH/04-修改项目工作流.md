# 04 修改项目的基本流程（软件 · 目录 · 连锁处理）

> **本项目的编译口径：一律线上编译（GitHub Actions），本机不装交叉工具链。**
> 本机只做三件事：**编辑文件** → **git push** → **下载 CI 产物用 mGBA 跑**。
> 所有 `make` 类命令都由 `.github/workflows/build-rom.yml` 在 GitHub 的 Ubuntu runner 上执行。
> **触发规则**：只有 push 到 `master` 会自动编译；`feature/*` 分支要出 ROM，得去网页手动 Run workflow（第 3 节第 5 步）。
>
> 结论先行：改这个项目只有 **5 个层级**，先定层级再动手，否则改完不知道为什么要动 8 个文件。
>
> | 层级 | 改什么 | 目录 | 需要软件 | 编译方式（全部线上） |
> |---|---|---|---|---|
> | ① 配置 | 游戏机制开关（代际、极巨化、孵蛋规则…） | `include/config/*.h` | VS Code | 勾 `clean_build` 全量重编（12–20 分钟） |
> | ② 数据 | 招式数值、道具、种族、队伍、野生分布 | `src/data/**`、`include/constants/**` | VS Code | 普通构建（8–12 分钟） |
> | ③ 脚本 | 对话、剧情、NPC、商店、战斗编排 | `data/maps/*/scripts.inc`、`data/scripts/*.inc`、`data/battle_scripts_1.s` | VS Code（或 Porymap 编辑地图/对象） | 普通构建（8–12 分钟）+ mGBA 实测 |
> | ④ 资源 | 图片、音乐、图块 | `graphics/**`、`sound/**` | Aseprite / MIDI 编辑器 | 普通构建（8–12 分钟） |
> | ⑤ 引擎 | 逻辑实现（新机制、AI、菜单） | `src/*.c`、`include/*.h` | VS Code | 普通构建 + 可选 `run_tests` |
>
> **铁律 5 条**：
> 1. 改动前先 `git checkout -b feature/xxx`，别在 `master` 上裸改——`master` 一 push 就自动编译一次，而且是"正式"那条线上，白烧 8–20 分钟。
> 2. 生成文件（`*.4bpp`、`*.lz`、`src/data/trainers.h`、`include/constants/map_groups.h` 等）**永远不要手改**，改输入。
> 3. 编译不过 ≠ 环境问题，先在 Actions 日志里看**第一行 error**，`-Werror` 会把警告当错误。
> 4. 删除比新增危险 10 倍：先删引用，再删定义。
> 5. 每次提交前 `git status` 确认没带进 `build/` 和 `.gba`。
>
> **为什么强制线上编译**：本机是 Windows，原生 MSYS2 编译比 Linux 慢一个数量级；装 WSL2 要下 1–2 GB 发行版、再装交叉工具链，且 WSL 与 Windows 文件系统互访会再慢 10 倍。CI 直接给一台预装好 `arm-none-eabi` 的 Ubuntu，同样的命令、同样的结果，本地零配置。

## 1. 软件清单（Windows 环境，零编译工具链）

| 用途 | 推荐软件 | 说明 / 坑 |
|---|---|---|
| **编译** | **GitHub Actions（不装任何本地工具链）** | 全部构建在 GitHub 的 Ubuntu runner 上跑，本机省下 1–2 GB 工具链和 WSL2。配置见 `02-GitHub-Actions线上编译.md` |
| 代码编辑 | **VS Code** | 装 C/C++ 扩展 + EditorConfig；本项目 `.editorconfig` 缩进为 **Tab**；也可以直接在 GitHub 网页上改（按 `.` 键开 Codespaces 式编辑器） |
| 版本控制 | Git（Git for Windows 自带 Git Bash） | 你当前就是这套；**push 即触发编译**，所以 commit 前想清楚 |
| 地图编辑 | **Porymap** | 读写 `data/maps/*/map.json` 与 `data/layouts/`；**注意**：expansion 独有字段（`region`、`requires_flash` 等）旧版 Porymap 可能不识别，保存后必须 `git diff` 复核 |
| 图块/图集 | Porymap 内置 tilemap 编辑器 + Aseprite | 图块必须索引色 |
| 像素图 | **Aseprite**（付费）/ GraphicsGale / LibreSprite（免费） | 输出必须是**索引色 PNG，≤16 色** |
| 音乐 | Anvil Studio / FL Studio / LMMS | 导出 `.mid`，再在 `sound/songs/midi/midi.cfg` 登记 |
| 运行测试 | **mGBA** | 本地只需要它来跑 CI 下载回来的 `.gba`；支持 `.sym` 符号调试 |
| 二进制对比 | HxD / 010 Editor | 改 `.bin`/`.gbapal` 时用 |
| 汉化文本 | Excel + Python（pandas / openpyxl） | `python_tools/` 那套，**本地跑，只改文本不改编译** |
| JSON 校验 | VS Code 内置（JSON schema 提示） | `map.json` 少个逗号就编不过 |

**不需要装**：WSL2、Ubuntu、`gcc-arm-none-eabi`、`devkitARM`、MSYS2、Cygwin、`make`。
装了也没用——本流程不执行任何本地 `make`，所有构建都在 Actions 里。

**不要用的**：Word / WPS 改 `.inc`/`.h`（会引入全角标点、BOM，CI 直接报 `unknown character`）；在线 JSON 美化器重排整个 `wild_encounters.json`（diff 会爆炸）。

> 关于 **Poryscript**（`.pory` 脚本语言）：本项目**没有**内置支持，也没有任何 `.pory` 文件。想用需要自己往 Makefile 加规则，属于"给自己挖坑"，不建议。

## 2. 环境准备（一次性，约 15 分钟）

### 2.1 本机只装这 4 个

```text
1. Git for Windows      → 提供 git 与 Git Bash
2. VS Code              → 编辑 .inc / .h / .c / .json
3. mGBA                 → 跑 CI 下载回来的 .gba
4. （按需）Porymap / Aseprite / MIDI 编辑器
```

### 2.2 线上编译环境（已在 workflow 里声明，你什么都不用装）

CI 每次运行会自己执行这段（`build-rom.yml` 里的 `Install toolchain` 步骤）：

```bash
# 这四行是 CI runner 内部执行的，你只需要知道它在装什么
sudo apt-get update
sudo apt-get install -y --no-install-recommends \
  build-essential binutils-arm-none-eabi gcc-arm-none-eabi \
  libnewlib-arm-none-eabi libpng-dev python3
```

| 包 | 为什么需要 |
|---|---|
| `binutils-arm-none-eabi` | `arm-none-eabi-as` / `ld` / `objcopy`，把 `.o` 链接成 GBA 可执行 |
| `gcc-arm-none-eabi` | `arm-none-eabi-gcc` / `g++`，编 C 与 `tools/` 里的 C++ |
| `libnewlib-arm-none-eabi` | 交叉编译用的 C 标准库头文件与实现 |
| `libpng-dev` | `gbagfx` 读 PNG 必需 |
| `python3` | `mapjson`、`wild_encounters_to_header.py` 等生成脚本 |
| `build-essential` | 编 `tools/` 里的本地工具（gcc/make，**非交叉**） |

### 2.3 开启 Actions 并放入 workflow（真正的一次性动作）

1. 打开 <https://github.com/ruina3s/pokeemerald-expansion/actions>
2. 点黄色横幅 **"I understand my workflows, go ahead and enable them"**
3. 把 `02-GitHub-Actions线上编译.md` 第 4 节的 `build-rom.yml` 提交到 `.github/workflows/`
4. `Settings → Actions → General → Workflow permissions` 选 **Read and write permissions**（发 Release 需要）

### 2.4 Git 双远端（你已经有）

```bash
git remote -v
# origin    https://github.com/ruina3s/pokeemerald-expansion.git          ← 你的 fork
# upstream  https://github.com/rh-hideout-chinese/pokeemerald-expansion.git ← 中文上游
```

## 3. 标准工作流（9 步，全程无本地编译）

```bash
# 0) 确保工作区干净，并同步远端
git status
git pull origin master

# 1) 开分支（命名建议：feature/xxx、fix/xxx、content/xxx）
#    注意：分支 push 不会自动编译（workflow 只监听 master），
#    所以分支上可以随便推，不会占 CI 队列；要出 ROM 得手动触发（第 5 步）
git checkout -b feature/my-new-npc

# 2) 改文件（见第 4 节场景手册）
#    ——VS Code 改 .inc/.h/.json；Porymap 改地图；Aseprite 改图
#    ——本步不产生任何编译，改完只是文本变化

# 3) 本地做"不花钱的自检"（替代原先的 make，30 秒内能查出的错误别浪费 CI）
git diff --stat                      # 改了哪些文件
grep -n "	" 改动文件 | head          # 确认缩进是 Tab（见第 9 节坑 1）
python3 -c "import json;json.load(open('data/maps/MyTown/map.json'))"   # JSON 语法
#    ↑ 只验语法，不编译。没有 python 就用 VS Code 的 JSON 报错提示

# 4) 提交并推送
git add -A
git commit -m "content: add gift NPC in LittlerootTown"
git push -u origin feature/my-new-npc

# 5) 手动触发编译（分支上验证就靠这一步）
#    网页：Actions → 左侧 Build ROM → 右侧 "Run workflow" → Branch 选 feature/my-new-npc
#          → build_mode 选 dev → Run workflow
#    命令行（装了 gh 的话一行搞定）：
#    gh workflow run build-rom.yml --ref feature/my-new-npc -f build_mode=dev

# 6) 等 CI 编译（8–12 分钟；勾了 clean_build 是 12–20 分钟）
#    浏览器打开：https://github.com/ruina3s/pokeemerald-expansion/actions
#    点最新一条 Build ROM 运行 → 看日志实时滚动 → 变绿即成功

# 7) 下载 ROM
#    同一次运行的页面底部 Artifacts → 点 rom-emerald-dev-feature-my-new-npc → 得到 zip → 解压出 .gba

# 8) mGBA 实测
#    mGBA 打开 .gba → 标题画面按 SELECT 用 Quickstart 秒进新游戏 → 走到改动点验证
#    include/config/quickstart.h 里 ENABLE_QUICKSTART = TRUE 才有这个快捷入口
#    需要现场造条件时：大地图按住 R 再按 START 打开调试菜单（dev 模式默认就有）

# 9) 合并
#    验证通过后开 PR，等 CI 的 build / test 全绿再合并到 master
#    合并那一刻还会自动编译一次——这是 master 上的"正式版本"，别在这里试错
```

**Quickstart 是开发期神器**：不用每次重开存档跑开场剧情。CI 出的 ROM → mGBA → 标题按 SELECT → 30 秒内到测试点。

**迭代节奏参考**（这是这套流程唯一的代价，提前知道就不焦躁）：

| 你改的东西 | 从触发到拿到新 ROM |
|---|---|
| 一句对话 / 一个脚本分支 | 8–12 分钟 |
| 一个 `.c` 实现 | 8–12 分钟 |
| 招式表 / 道具表 | 8–12 分钟 |
| `include/config/*.h` | 12–20 分钟（要勾 `clean_build`） |
| 勾了 `run_tests` | 再加 3–6 分钟（首次要现编 mGBA，+15–20 分钟） |

> **线上编译没有"增量"这回事**：每次都从干净检出开始，所以改一行和改一百行几乎一样慢。
> 想批量验证时：**一次 commit 改完多个点**，别一个错别字触发一次。

### 3.1 用游戏内调试菜单造测试条件（省掉一半重开档）

改完脚本要验证，最烦的是"条件不具备"：没到那个城镇、没有那只宝可梦、剧情旗标没置位。这些**全部可以用调试菜单现场造**，不用改代码也不用打金手指。

前提：拿到的是 **`dev` / `debug`** 模式编出的 ROM（文件名不带 `-release`）。`dev` 是默认值，正常下载的产物就是。

| 我想…… | 菜单路径 | 说明 |
|---|---|---|
| 直接去某张地图 | 常用功能… → 飞往地图 / 瞬移到地图 | 跳图最快，不用走路线 |
| 拿到某只宝可梦 | 获取… → 获得宝可梦(简易/详细) | 「详细」可指定等级、性格、个体、招式、异色 |
| 把队伍改强 | 同行宝可梦… → 编辑宝可梦 / 回忆招式 | 改特性、隐藏特性、亲密度、异常状态；配招用「回忆招式」 |
| 背包塞满道具 | 电脑/包包… → 填充… | 测道具效果、测商店 |
| 卡在剧情某一步 | 标志与变量… | 改 flag / var；还有「无视地形阻碍」「不再遭遇宝可梦」「对训练家隐身」等开关 |
| 打某个训练家 | 训练家… → 尝试进入战斗 | 不用跑到他面前 |
| 测野生分布 | 遇敌… → 大量出现… | 可设物种、地图、等级、概率、剩余天数 |
| 跑自己写的测试脚本 | 脚本… → 脚本 1~8 | 对应 `data/scripts/debug.inc` 里的 `Debug_EventScript_Script_1`…`_8` |

**自定义测试入口的写法**：`data/scripts/debug.inc` 里 8 个脚本现在都只有 `release` + `end`（空壳），把中间换成你的逻辑即可。例如把 `Debug_EventScript_Script_3` 改成——

```asm
Debug_EventScript_Script_3::
	givemon SPECIES_PIKACHU, 50           @ 给一只 50 级皮卡丘（第 2 参数是等级）
	setflag FLAG_SYS_POKEMON_GET          @ 置"已获得宝可梦"旗标，否则菜单/图鉴可能异常
	msgbox Debug_Text_MyTestDone, MSGBOX_DEFAULT   @ 弹一句提示，确认脚本真的跑到了
	release                               @ 和 debug.inc 里其它脚本保持一致
	end                                   @ 脚本必须有 end，否则会往下执行到别人的脚本

Debug_Text_MyTestDone:
	.string "测试脚本执行完毕。$"           @ $ 是文本结束符，漏了会读穿到下一段
```

按键：**大地图按住 `R`，再按 `START`**。战斗内是 `SELECT`，能力页是 `SELECT`。整套机制的开关与改键方法见 `02-GitHub-Actions线上编译.md` 第 4.3 节。

## 4. 场景操作手册（12 个高频改动）

### 场景 1：改一句对话

| 项 | 内容 |
|---|---|
| 改哪里 | `data/maps/<Map>/scripts.inc` 末尾的 `Xxx_Text_Yyy:` 段 |
| 软件 | VS Code（或 Porymap 的文本编辑器） |
| 写法 | `.string "第一行\n第二行$"`（`$` 结尾、`\n` 换行、`\p` 翻页） |
| 连锁 | 无 |
| 验证 | push → CI 编译（约 8–12 分钟）→ 下载 artifact → 游戏内对话 |
| 坑 | 单行太长会超框；`charmap.txt` 里没有的字编不过 |

```asm
MyTown_Text_Hello:                        @ 文本标签（单冒号），脚本里用 msgbox MyTown_Text_Hello 引用
	.string "你好！\n今天天气不错。$"      @ \n = 换行；\p = 翻页；$ = 结束符（少了会读到下一段文本）
```

### 场景 2：加一个 NPC

| 项 | 内容 |
|---|---|
| 改哪里 | ① `data/maps/<Map>/map.json` 的 `object_events` 数组<br>② 同目录 `scripts.inc` 写脚本 |
| 软件 | Porymap（可视化摆人）或 VS Code（手写 JSON） |
| 连锁 | `local_id` → 自动生成 `LOCALID_*` 常量（`include/constants/map_event_ids.h`，勿手改） |
| 验证 | push → CI 编译（约 8–12 分钟）→ 下载 artifact → 进图看人是否出现、对话是否触发 |

```json
{
  "local_id": "LOCALID_MY_TOWN_GIRL",
  "graphics_id": "OBJ_EVENT_GFX_GIRL_1",
  "x": 10, "y": 6, "elevation": 3,
  "movement_type": "MOVEMENT_TYPE_WANDER_AROUND",
  "movement_range_x": 1, "movement_range_y": 1,
  "trainer_type": "TRAINER_TYPE_NONE",
  "trainer_sight_or_berry_tree_id": "0",
  "script": "MyTown_EventScript_Girl",
  "flag": "0"
}
```

| 字段 | 填什么 |
|---|---|
| `local_id` | 本图内唯一名，脚本里用 `LOCALID_MY_TOWN_GIRL` 指代（`mapjson` 自动生成常量） |
| `graphics_id` | 外观，可选值见 `include/constants/event_objects.h` |
| `x` / `y` / `elevation` | 格坐标 + 高度层（地面一般 `3`） |
| `movement_type` | `MOVEMENT_TYPE_WANDER_AROUND` 随机走动；`MOVEMENT_TYPE_FACE_DOWN` 站桩 |
| `movement_range_x/y` | 游走半径，`1` = 上下左右各 1 格内晃 |
| `trainer_type` | 普通人写 `TRAINER_TYPE_NONE`；会追上来开战写 `TRAINER_TYPE_NORMAL` |
| `trainer_sight_or_berry_tree_id` | 非训练家写 `"0"`；训练家填视野格数 |
| `script` | 交互时执行的脚本名（`::` 定义的那个，不带冒号） |
| `flag` | 该旗标置位时隐藏；`"0"` = 永不隐藏 |

```asm
MyTown_EventScript_Girl::              @ 入口：map.json 的 script 字段指向这里
	lock                                @ 冻结玩家与 NPC，防止对话时被撞走
	faceplayer                          @ NPC 转向玩家
	msgbox MyTown_Text_Hello, MSGBOX_DEFAULT   @ 弹标准对话框，等玩家按 A
	release                             @ 解冻（与 lock 配对，漏了卡死）
	end                                 @ 结束
```

> `graphics_id` 可选值在 `include/constants/event_objects.h`（`OBJ_EVENT_GFX_*`）。想加**全新外观**还要动 `graphics/object_events/pics/**` + `src/data/object_events/object_event_graphics_info*.h`，这属于场景 10。

### 场景 3：新建一张地图

| 项 | 内容 |
|---|---|
| 改哪里 | ① `data/layouts/<Layout>/`（`map.bin` + `border.bin`）<br>② `data/layouts/layouts.json` 登记布局<br>③ `data/maps/<Map>/map.json` 建地图<br>④ `data/maps/map_groups.json` 登记到分组 |
| 软件 | **Porymap**（新建地图向导会一次做完这 4 步） |
| 连锁 | `mapjson` 自动生成 `MAP_*` / `LAYOUT_*` 常量、`map_groups.h`、`map_group_count.h` |
| 验证 | push → CI 编译（约 8–12 分钟）→ 下载 artifact → 用 `warp MAP_NEW, 0, x, y` 或调试菜单跳过去 |

手写要点（`layouts.json` 一条）：

```json
{
  "id": "LAYOUT_MY_TOWN",
  "name": "MyTown_Layout",
  "width": 20, "height": 20,
  "primary_tileset": "gTileset_General",
  "secondary_tileset": "gTileset_Petalburg",
  "border_filepath": "data/layouts/MyTown/border.bin",
  "blockdata_filepath": "data/layouts/MyTown/map.bin",
  "layout_version": "emerald"
}
```

| 字段 | 填什么 |
|---|---|
| `id` | 布局常量 `LAYOUT_*`，`map.json` 里用它引用 |
| `name` | 布局名（与目录名一致最省心） |
| `width` / `height` | 地图宽高（单位：格，不是像素）；改尺寸必须同时重做 `map.bin` |
| `primary_tileset` | 主图块集（决定地形基底层） |
| `secondary_tileset` | 副图块集（决定建筑/装饰，容量更小） |
| `border_filepath` | 地图边界外那圈"黑边"图块数据 |
| `blockdata_filepath` | 真正的图块索引数组（每格 2 字节） |
| `layout_version` | 固定 `emerald`；跨版本兼容用 |

> `map.bin` 是**二进制**图块索引（每格 2 字节），**不要手改**。要用 Porymap 或自写脚本生成。

### 场景 4：改野生分布

| 项 | 内容 |
|---|---|
| 改哪里 | `src/data/wild_encounters.json` |
| 软件 | VS Code（大文件）/ Porymap 的野生分布编辑页 |
| 连锁 | 自动生成 `src/data/wild_encounters.h` + `include/constants/wild_encounter.h` |

## 5. 变更影响矩阵（改完要等多久）

CI 每次从**干净的工作区**开始，没有本地 `.o` 可复用，所以耗时由"改了什么"决定。下表是 4 核 runner 的实测估算口径：

| 改动位置 | CI 需要重做的部分 | 端到端耗时（含排队+checkout） | 说明 |
|---|---|---|---|
| `data/maps/*/scripts.inc` | 该地图事件数据 + 汇编 + 链接 | **8–12 分钟** | 每次都要重编 385 个 `.c` 的大部分，所以不会像本地增量那样只要 10 秒 |
| `data/battle_scripts_1.s` | `battle_scripts_1.o` + 链接 | **8–12 分钟** | 同上 |
| `src/*.c` 单个文件 | 该 `.o` + 链接 | **8–12 分钟** | 首次跑完工具缓存后稳定在这个区间 |
| `src/data/*.h` | 引用它的 `.o` | **10–15 分钟** | 表驱动数据常被 `data.o` 等大文件包含 |
| `graphics/**/*.png` | 该图片转换 + 链接 | **8–12 分钟** | 图形转换是 CI 最大瓶颈（1.1 万张 PNG 单线程） |
| `include/config/*.h` | **几乎所有 `.c`** | **15–22 分钟** | 必须配合 `clean_build` |
| `include/constants/*.h` | 大部分 `.c` | **13–20 分钟** | 建议配合 `clean_build` |
| 新增 `.c` 文件 | Makefile 用 wildcard 自动收集 | **8–12 分钟** | 不用改 Makefile |
| `ld_script_modern.ld` | 全量链接 | **10–18 分钟** | 建议配合 `clean_build` |

> 所以：**能一次 commit 改完就别 push 多次**。线上编译的固定成本是 8 分钟起，跟改一行还是改一百行差别不大——这是它和本地增量编译最大的不同，也是唯一的代价。

## 6. 线上编译能力对照表（哪些能远程做、哪些必须本机）

| 你想做的事 | 在 CI 里怎么做 | 能否纯线上 |
|---|---|---|
| 编译 `pokeemerald.gba` | `build-rom.yml` → `make -j$(nproc) -O all` | ✅ 完全线上 |
| 编译发布版（LTO） | 手动触发时 `build_mode = release` → `make RELEASE=1`（**调试菜单会被关掉**） | ✅ |
| 编译火红 / 叶绿 | 手动触发时 `version = firered / leafgreen` | ✅ |
| 全量重编（tidy 后重来） | 手动触发时 `clean_build = true` → `make tidy && make all` | ✅ |
| 跑测试套件 | 手动触发时勾 `run_tests = true` → `make -j$(nproc) check` | ✅ |
| 生成 `.sym` 符号表给 mGBA | 默认 `make all` 已产出 `.elf/.map`；要 `.sym` 勾 `make_syms` | ✅ |
| 看编译器具体报错 | Actions 日志里逐行滚动，可展开 `Build ROM` 步骤 | ✅ |
| 把 ROM 下载到本地 | 运行页底部 Artifacts → `rom-emerald-dev-<ref>` | ✅ |
| **运行游戏验证玩法** | 不能——runner 没有屏幕 | ❌ 本机 mGBA |
| **用调试器断点** | 不能（无 GUI） | ❌ 本机 mGBA + `.elf` |
| **真正逐字节匹配原版 ROM** | 不能（无 `baserom.gba`，且涉版权） | ❌ 不做 |

> 一句话：**CI 负责"能不能编出来"，本机负责"编出来对不对"**。

```bash

git fetch upstream
git checkout master
git merge upstream/master           # 冲突多时用 rebase，但 rebase 已推送的分支要 force push

合并后必做：

2. 看 `migration_scripts/<新版本>/README.md`，按需跑迁移脚本（这一步在**本机**跑，它只是改文本，不编译）

**你的改动和上游冲突时**：优先保留上游重构，把自己的改动重写到新结构上。硬顶冲突（保留自己的旧实现）等于自断升级路径。

	lock                                    @ 冻结玩家与所有 NPC，防止对话时乱走
	faceplayer                              @ 让这个 NPC 转向玩家
	goto_if_set FLAG_RECEIVED_MY_TOWN_GIFT, MyTown_EventScript_GiftDone   @ 拿过了就跳走
	giveitem ITEM_POTION, 3                 @ 给 3 个伤药；结果写入 VAR_RESULT
	goto_if_eq VAR_RESULT, FALSE, Common_EventScript_ShowBagIsFull        @ 背包满则提示并结束
	setflag FLAG_RECEIVED_MY_TOWN_GIFT      @ 记下"已领过"
	msgbox MyTown_Text_GiftThanks, MSGBOX_DEFAULT                          @ 道谢
	release                                 @ 解冻（漏了会卡住玩家）
	end                                     @ 脚本结束

MyTown_EventScript_GiftDone::
	msgbox MyTown_Text_GiftAlready, MSGBOX_DEFAULT   @ 已领过的台词
	release
	end

MyTown_Text_GiftThanks:
	.string "这个给你，路上小心！$"        @ $ 是文本结束符，必须写

MyTown_Text_GiftAlready:
	.string "药已经给过你啦。$"
```

**④ 提交 + 推送（推送 = 开始编译）**

```bash
# 只 add 这 3 个改过的文件，别用 git add -A（容易把临时文件带进去）
git add data/maps/MyTown/map.json data/maps/MyTown/scripts.inc include/constants/flags.h
# message 用 "前缀: 描述" 格式，Actions 列表里一眼能看出这次改了什么
git commit -m "content: add gift NPC in MyTown"
# push 到远端 —— 这一下就触发了 CI 编译
git push -u origin content/gift-npc
```

1. 打开 <https://github.com/ruina3s/pokeemerald-expansion/actions>
2. 点最新一条 `Build ROM`（标题会带你的 commit message）
3. 等 8–12 分钟，绿色对勾 = 成功
4. 页面底部 **Artifacts** → `rom-content-gift-npc` → 下载 zip

**⑥ 本机验证**

```text
解压 → mGBA 打开 .gba → 标题画面按 SELECT 快速开局
     → 传送到 MyTown（或走到该地图）→ 与 NPC 对话
     → 第一次给 3 个伤药；第二次说"已经给过你啦"
```

CI 绿 + 游戏内验证通过 → 开 PR → 等 `build` / `test` job 全绿 → merge 到 `master`。
